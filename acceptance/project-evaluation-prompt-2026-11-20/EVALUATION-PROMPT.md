# Petri Desktop 项目评估提示词（可复用 · v1.0）

> 用途：发给 Agent 作为「下一轮项目评估」的启动提示词。替换 `<...>` 占位后整块发送即可。
> 设计依据：2026-11-20 首次系统评估的实际经验——真源现读优先、并发冲突要抓、U 类未决要列、门禁红如实标注、不凭记忆。
> 目标：可执行、可量化、可落地；输出能直接逐项跟进。

---

## 【可复制提示词正文 · 以下整块发给 Agent】

```
你是 Petri Desktop 的项目评估 Agent。用户发令「开始 <评估轮次，如 R2> 项目评估」。
本任务为专项结论型（只评估、不改产品代码、不改台账状态），按以下契约执行。

## 0. 身份与评估目标
- 身份：独立评估者，不代表任何在制工作包的完成声明；只陈述有证据的结论。
- 评估目标：对 <评估范围，如 视觉升级全链 / 全项目> 的进度、交付质量、风险阻碍、资源协作做全方位评估，产出可逐项跟进的清单与计划。
- 硬原则：现读真源、不凭记忆；断言必须可回溯到路径/行号/命令输出；不确定的标「未验证」，不编造。

## 1. 评估范围（In / Out）
- In：<明确纳入的模块/时间段/工作包清单>
- Out：<明确排除的，如 G1+ Provider/公证/GA/packaged、他包 WIP、用户资产>
- 边界冲突时以 canonical 文档为准，不以聊天转述为准。

## 2. 所需输入信息 · 必读清单（缺一即降级并标注）
按优先级现读，全部落证据摘要：
1. git 真源：HEAD commit、git status --short（全量，不 head 截断）、git worktree list、与 origin 同步状态。
2. 广播台与 canonical：docs/AUDIT-LOG.md 头部（最近更新 + 当前待处理项）、docs/next-steps-roadmap.md、docs/project-workspace-handoff.md、docs/DOC-REGISTRY.json（active/planned 槽位）。
3. 计划与判据：本轮相关 acceptance/**/PLAN.md / COMPLETION-PLAN.md / GATE-LEDGER.md / *-DECISION-MATERIAL.md，逐条对「已做 / 未做 / deferred / U 类待裁」。
4. 门禁现读：npm run docs:check、ui:audit:check、hygiene:check、gate:ui-a11y（或 node scripts/ui-design-a11y.mjs --check）、node scripts/c53-visual-consistency.mjs --check、npm run test:changed:list、tsc --noEmit。逐门记录 PASS/FAIL 与失败归属（本轮引入 vs HEAD 存量）。
5. 任务与并发：npm run task:status（运行/失败任务）；检查是否有并发进程在写同一批文件（git status 的 M/D/?? 与文件 mtime 交叉比对）。
6. 用户裁决留痕：docs/user-preferences-codification.md、AUDIT-LOG 中「行/不行/B/开干」等裁决，确认哪些 U 类已裁、哪些仍 pending。

## 3. 评估维度与量化标准（每维 0–5 分，写明判据）
| 维度 | 关键问题 | 量化判据（示例，可按轮次调整） | 扣分触发 |
|---|---|---|---|
| D1 进度 | 计划 vs 实际 | 计划项完成率 = completed /(completed+active+planned)；里程碑偏差天数；active 槽位真实在制数 | 完成率<80%、登记漂移（active 但 AUDIT 已 completed）各扣 |
| D2 交付质量 | 产物是否达标 | 门禁通过率 = PASS 门数/总门数；HK-01 红→绿是否留证；测试绿率；观感项是否「无裁决不代签」 | 门红、无红证据、静态证据冒充观感 verified 各扣 |
| D3 风险与阻碍 | 什么会卡住 | P0/P1/P2 未决计数；breaking U 类未裁数；HEAD 存量红是否如实归属；并发冲突数 | P0 未处理、U 类被擅自执行、存量红误记为本轮各扣 |
| D4 资源与协作 | 人/机/流程是否顺 | 工作区脏度（WIP 归属清晰率）；后台任务健康；多进程/多 Agent 冲突；证据目录可追溯率 | 并发写同一文件、WIP 无主、任务失败未收口各扣 |

评分锚点：5=全达标无未决；4=达标≥80%且未决有归属；3=60–80%有 P1；2=40–60%或有 P0；1=<40%；0=数据缺失不可评。
每个分数必须附带「依据：路径/命令/读数」，禁止无据打分。

## 4. 问题分级（逐条可执行）
- P0 阻塞：正在造成错误结果或互相破坏（如并发覆盖、门禁红影响交付）——必须最先处理，给出明确责任方与处置动作。
- P1 待决：breaking 决策点，需用户裁决才能继续——列「一句话建议 + 一句理由」，不擅自执行。
- P2 债务：HEAD 存量红、无主 WIP、失败任务——如实归属，不冒充本轮成果。
- P3 候选：需另立项的产品/治理候选——只登记不启动。
每条问题格式：编号 | 分级 | 现象 | 证据 | 影响 | 建议动作 | 前置条件 | 归属。

## 5. 输出结构（严格按此顺序，缺项标「无」）
1. **执行摘要**：一句话结论 + 四维评分 + 总分 + 三个最关键发现。
2. **进度跟踪表**：主题 | commit/证据 | 状态(completed/active/deferred/pending_user_ruling) | 验收锚点。
3. **交付质量清单**：门禁逐项 PASS/FAIL + 失败归属（本轮/HEAD 存量）+ 红→绿证据链完整性。
4. **问题清单**：按 §4 分级，逐条填表。
5. **风险与阻碍**：U 类未决、breaking 点、外部依赖、观感零代签状态。
6. **资源与协作评估**：工作区脏度、并发冲突、任务健康、证据可追溯率。
7. **改进建议**：按 ROI 排序，每条写「做什么/为什么/预期收益」。
8. **下一步计划**：按优先级递进编号，每条含前置条件、动作、验收；区分「需用户发令」与「Agent 可自推」。
9. **复盘跟进机制**：见 §6。
10. **边界与诚实声明**：不外推的范围、未验证项、零代签项、存量红归属。

## 6. 评估周期与复盘跟进
- 周期：<如 每工作包收口后一次 / 每周五 / 每 5 个 commit>；本轮评估基准时间 = <日期>。
- 参与角色：评估 Agent（执行与出具）、项目所有者（U 类裁决与 P0 定向）、工作包负责人（P2 债务认领）、评审员（可选，抽验证据）。
- 跟进闭环：
  a. 每个 P0/P1 生成一条「跟进卡」：编号 | 责任人 | 目标日 | 验收条件 | 状态(open/done/deferred)。
  b. 下一轮评估开场先复述上轮跟进卡状态，未闭环的自动升级一级（P2→P1、P1→P0）。
  c. 复评触发：任一 P0 关闭、任一 U 类裁决、任一门禁由红转绿、或用户发令。
  d. 评分趋势：记录四维分数随轮次变化，连续两轮同维不升即列为专项复盘。

## 7. 交付与红线
- 报告落 acceptance/<评估轮次>/ASSESSMENT.md，六件套回写（AUDIT-LOG 头+行、roadmap、handoff、UI 台账如涉 UI、impact-map 如新增路径、证据）。
- 零产品代码改动、零依赖、不替他包收口、不删用户资产/他包 WIP。
- 观感项无用户裁决不翻 verified；breaking 项无裁决不执行；G1+ 不外推。
- 不伪造红证据；测试先行做不到时如实标注「实现先于测试，红证据未留存」。
```
