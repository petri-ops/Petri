# BioF3 Codex 式 AI 生信工作台方向文档

## 1. 总目标

BioF3 的下一阶段方向是：

> Codex 式工作台交互 + BioF3 固定插件/标准 workflow + 项目级可复现记录。

最终形态不是把 BioF3 改成一个通用聊天机器人，也不是推翻原来的云平台页面，而是把 BioF3 升级为一个以项目为中心、由 Agent 协作推进、由固定插件系统产生可复现结果的 AI 生信工作台。

用户体验目标：

> 用户不再面对一堆分散工具入口，而是在一个项目里，和 AI 生信分析搭档一起推进数据分析、查看结果、解释图表、沉淀可复现记录。

## 2. 产品定位

BioF3 保留原有“传统生信云平台”的专业能力，同时新增 Codex 式主工作台作为日常入口。

- 原云平台页面负责专业模块、细粒度配置、工具管理、管理后台。
- Codex 式工作台负责项目上下文、Agent 协作、任务编排、结果查看、连续分析链路。
- 插件系统负责后续生信能力扩展。
- Job/Artifact 系统负责可复现记录。

一句话：

> Agent 是自然语言操作层和分析协作层，固定插件和 workflow 才是真正的计算与结果来源。

## 3. 不能改变的底线

BioF3 不能变成“AI 随意写脚本、随意生成结果”的产品。

必须坚持：

- 所有正式分析必须落到已注册插件、标准 workflow 或受控执行器。
- 每次分析必须记录 projectId、toolId、插件版本、参数、输入、输出、日志、状态。
- 聊天区可以解释和编排，但不能替代可复现计算链路。
- Agent 不能绕过参数确认直接执行重操作。
- 结果必须可以回看、下载、复现、追踪来源。

推荐原则：

> AI 负责理解意图、选择工具、填参数、串流程、解释结果；BioF3 插件系统负责真实计算和产物生成。

## 4. 工作台信息架构

`/project/:projectId` 是新的核心工作台页面。

### 左侧：项目与资源

职责：

- 我的项目列表
- 当前项目基本信息
- 当前项目数据集
- 当前项目文件入口
- 当前项目分析历史入口
- 项目切换

左侧不是营销区，也不是大面积介绍页。它应该像 Codex 的 workspace/thread sidebar 一样，用于快速切换上下文和定位资源。

### 中间：Agent 主工作区

职责：

- 用户输入分析目标
- Agent 展示理解、计划、参数确认、执行进度
- Agent 在聊天里交付结果卡片
- 用户继续追问、解释、调整、推进下一步

中间区域是主舞台。Copilot 不应再只是浮窗，而应该是项目内的核心交互入口。

### 右侧：Artifacts / 结果查看器

职责：

- 文件树
- 分析结果图
- CSV/表格预览
- 日志
- 参数记录
- 下载入口
- 下一步推荐

右侧面板要和聊天区强联动：

- 点击聊天里的“查看结果”，右侧打开对应 job。
- 点击聊天里的“查看文件”，右侧打开对应 artifact。
- 右侧当前结果要反向注入 Agent 上下文。
- 用户问“解释这个图”时，Agent 知道当前正在看的结果。

## 5. Codex 式核心交互标准

### 5.1 项目级对话隔离

每个项目应有独立的 Copilot conversation。

要求：

- conversation 表支持 `project_id`。
- `/api/ai/conversations` 支持按 `project_id` list/create。
- `/project/:projectId` 中的 Copilot 只展示当前项目相关对话。
- 切换项目时，对话、上下文、结果查看都随项目切换。
- 非项目页面仍保留全局 Copilot 行为。

### 5.2 聊天结果卡片

工具运行完成后，聊天区必须出现可操作的结果卡片。

卡片至少包含：

- 工具/分析名称
- 运行状态
- 关键产物数量或简要结果
- 查看结果
- 查看文件
- 下载
- 继续下一步

卡片点击行为：

- `查看结果`：右侧切到 results tab，并打开对应 job。
- `查看文件`：右侧切到 files tab，并定位对应 artifact。
- `继续下一步`：把标准下一步 prompt 发送给 Agent。

聊天卡片不是装饰，它是 Agent 把工作产物交付给用户的主要方式。

### 5.3 Artifact 与结果查看同步

Artifact 是工作台的基本产物单位。

推荐字段：

- artifactId
- projectId
- jobId
- toolId
- type: image / table / log / report / file / params / directory
- title
- path 或 url
- previewUrl
- mimeType
- size
- createdAt
- metadata

右侧查看器至少支持：

- 图片预览和放大
- CSV/TSV 表格预览
- 日志查看
- 参数 JSON 查看
- 下载
- 打开所在目录或文件列表

### 5.4 参数确认卡片

涉及写操作、运行分析、删除数据、覆盖文件、调用重计算时，Agent 必须先展示参数确认卡片。

参数确认卡片要求：

- 显示工具名和目的
- 显示参数表单
- 支持用户微调参数
- 显示输入数据和输出位置
- 显示风险或耗时提示
- 支持确认、取消

确认后才能调用插件或 workflow。

### 5.5 执行过程可见

Agent 执行过程要可见、可追踪。

至少展示：

- 已理解目标
- 拟调用的插件/workflow
- 等待确认
- 已提交 job
- running / done / failed
- 失败原因
- 可恢复动作

长期目标是形成项目级 timeline：

> 计划 -> 参数确认 -> job 提交 -> 运行日志 -> artifact 生成 -> 结果解释 -> 下一步建议。

## 6. 插件系统的长期角色

UI/交互底座稳定后，后期主要功能迭代应集中在插件系统。

插件应声明：

- 插件 id
- 名称和描述
- 版本
- 支持的 modality
- 输入 schema
- 参数 schema
- 输出 artifact schema
- 资源需求
- 运行器类型
- 示例数据
- 可视化组件或结果查看方式
- 可接续的下一步 workflow

理想状态：

> 每新增一个生信能力，不需要重做页面，只需要注册插件、声明参数、声明输入输出和 artifact 展示方式，Agent 与工作台就能自然接入。

## 7. 原云平台页面如何保留

不推翻原页面。

保留并重新定位：

- `/tools`：工具库和插件浏览。
- `/single-cell`：传统单细胞专业模块。
- `/spatial`：传统空间组学专业模块。
- `/figcode`：图表与代码资源库。
- `/admin`：管理后台。
- `/project/:projectId`：新的默认工作台。

用户可以继续按传统云平台路径使用；新工作台只是把最常见的分析路径变成 Agent 驱动。

## 8. MVP 验收标准

第一阶段最小闭环：

> 在一个项目里，用户让 Agent 跑一个固定插件分析；参数确认后生成 job；job 完成后聊天区出现结果卡片；点击卡片右侧打开结果图/表/日志；用户继续问“解释这个结果”，Agent 能基于当前项目和当前结果回答。

验收项：

- `/project/:projectId` 是三栏工作台。
- Agent 对话按项目隔离。
- Agent 能读取当前项目、数据集、任务历史、当前结果。
- 工具运行必须经过参数确认。
- job 记录 projectId、toolId、params、status。
- artifact 能在右侧查看。
- 聊天结果卡片能打开右侧结果。
- 结果查看状态能反向注入 Agent 上下文。
- 原云平台页面仍可访问。

## 9. 分阶段实施路线

### Phase A：方向固化与现状审计

- 固化本方向文档。
- 对照当前代码审计项目工作台、Copilot、conversation、job、artifact、插件系统。
- 更新执行计划。

### Phase B：项目级对话隔离

- conversation schema 增加 project_id。
- list/create/get-or-create 支持 project_id。
- CopilotChat 在项目工作台内传入当前 projectId。
- 切换项目时重置/切换 active conversation。

### Phase C：聊天结果卡片

- 定义 chat artifact/result card 数据结构。
- 工具完成后把 job/artifact 信息写入消息 meta。
- 聊天消息渲染可点击结果卡片。
- 对话历史恢复后卡片仍可点击。

### Phase D：右侧 Artifact 联动

- 提供工作台级 artifact selection state。
- 聊天卡片点击后打开右侧结果。
- 右侧选择结果后更新 Copilot context。
- 支持图片、表格、日志、参数、下载。

### Phase E：参数确认与可复现执行

- 完善参数确认卡片。
- 将确认后的最终参数写入 job。
- 展示工具版本、输入、输出、日志。
- 失败状态给出可恢复建议。

### Phase F：插件 schema 标准化

- 统一插件输入/参数/输出 schema。
- 统一 artifact schema。
- 让 Agent 只能通过注册能力调用正式分析。
- 支持 workflow chain 和下一步推荐。

## 10. 后续工作方式

涉及以下内容时，必须先 plan 再实现：

- 工作台布局与交互
- Agent 行为
- 插件调用
- conversation 数据模型
- job/artifact 模型
- 结果查看器
- 可复现链路

标准流程：

1. 读代码现状。
2. 对照本方向文档。
3. 写小步实施 plan 和验收标准。
4. 实现一个可验证闭环。
5. 运行检查或构建。
6. 更新执行计划状态。

小 bug 可以直接修；涉及产品主线的改动必须先有计划。

## 11. 设计口径

BioF3 可以学习 Codex 的工作台体验，但不做像素级复制。

应该复刻的是：

- 聊天作为主舞台
- 结果链接可点击
- 右侧 artifact 查看
- 项目/线程上下文连续
- 任务执行过程透明
- 历史可恢复

BioF3 自己必须强化的是：

- 生信插件标准化
- 科研可复现
- 参数可审计
- 图表/表格/日志专业查看
- 分析链路推荐
- 多组学项目管理

最终目标：

> 像 Codex 一样自然协作，像专业生信平台一样可信复现。
