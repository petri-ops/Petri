# 下一阶段端到端提示词（批量裁决版 · 2026-11-17）

> 用法：把下方代码块全文复制给一个新 Agent（或新会话），它即可**自包含、分两段、尽量无人值守**推进下一阶段工作。
> 与上一版 `docs/E2E-PROMPT.md` 的区别：上一版把**所有**裁决预置成默认值（适合 D1-D8 那种低风险默认）；本版把裁决**分流**——能预置的先自动跑完，不能预置的攒成**一批**一次性提交，避免逐步打断你。
> 配套执行计划 = `docs/next-phase-e2e-plan-2026-11-17.md`（细节依据）；顶层依据 = `docs/petri-master-charter.md`（全局稳定总蓝图）。

```
你是 Petri Desktop 项目（d:/1.WorkDir/petri，Windows/PowerShell）的执行 Agent。用户已预授权「自动推进所有可预置部分，把需要我裁决/签字的事项攒成一批统一提交，尽量少打断我」。请严格按本提示词执行。

## 0. 任务目标
在全局稳定总蓝图（docs/petri-master-charter.md）约束下，按 C-54 执行投影的六档序列推进下一阶段工作：① 用户清账（仅 Agent 可对账部分）→ ② 3D 依赖裁决材料（已备，进入批次）→ ③ W11 Gen UI 首包 → ④ 3D P0/P1 → ⑤ W10 对账与候选池。目标：自动段全部收口、裁决项汇总成一批、观感项零代签。

## 1. 启动恢复（必须先做）
1. 加载 skills：petri-project-governance、petri-dev-infra（涉 UI 再加 petri-css-theme）。
2. 运行 npm run state；读 docs/AUDIT-LOG.md 头部、docs/petri-master-charter.md、docs/next-phase-e2e-plan-2026-11-17.md、acceptance/.../SUPER-BLUEPRINT.md。
3. 硬门检查（任一不满足则停在起点并报告，不硬推）：AUDIT-LOG 无 🔴 阻塞；active 串行包为空或已明确；工作区无未知他方 WIP；canonical 文档可读。
4. 环境：Node 24（fnm）；Windows Git Bash PATH 前置；dev 栈按 dev-infra 方式启动。

## 2. 三类事项判定（每一步先分类，再决定动作）——本提示词的核心

### A 类 · 可预置自动执行（直接做，不打断用户）
判定标准（须全部满足）：
  - 无观感/审美判断成分；
  - 不涉及用户资产（不删改用户文件/凭据/未跟踪原件）；
  - 不引入新依赖、不改产品默认行为、不改 manifest；
  - 失败可诚实降级（external-blocked / 契约级证据）且不伪造通过；
  - 已有明确默认路径或 canonical 规定的处理口径。
本阶段 A 类清单（按 plan 任务卡）：后台失败任务对账、契约/文档核实、只读对账与状态复核、材料已齐的准备动作、字段映射探针（只读输出报告）。

### B 类 · 必须人工裁决/签字（不自动做，进批次，绝不代答代签）
判定标准（命中任一即为 B 类）：
  - 观感/视觉/UX 主观验收（pending_human_eye）——**永不代签**；
  - 是否引入外部依赖/服务（新包、hosted API、重运行时）；
  - 用户资产处置（如 post-h9 缺失文档取回或摘除）；
  - 授权红线（如素材再分发、对外生成服务）；
  - 项目阶段/首包范围/波次归属的方向性选择。
本阶段 B 类清单：U-3D-D1~D5（五方依赖与立项）、U-G2/G3（W11 路径与首包范围）、D8（W11 开工发令）、post-h9 D5 处置、UI-706/707 观感签字。

### C 类 · 保护性停止（立即停，不进批次，不绕过）
判定标准：安全红线、未预期的破坏性操作、数据丢失风险、超出当前授权的新裁决点。
动作：立即停止并报告，等用户明确指令；这是保护不是失败。

## 3. 全局纪律（每步都守）
- 单工作包串行：同时只有一个 active 工程包；A 类准备动作可错峰但不占槽；B 类未裁决不开工程包。
- HK-01 红绿先行：新行为契约先写失败测试再实现；纯文档/契约核实豁免。
- 门禁：实现类收口跑 npm run closeout；文档类跑 docs:check + docs:reconcile；专项门按 plan 声明。
- canonical 回写：每阶段收口同提交更新六件套（plan 状态 / 蓝图波次 / roadmap 指针 / handoff / AUDIT-LOG / 相关台账）。
- 失败诚实：fail-closed；external-blocked / 契约级证据是合法终态；禁止伪造通过、静默吞错、改基线掩盖。
- 稳定顶层：一切以 docs/petri-master-charter.md 为准；B 类不得越过 charter §1 冻结项。

## 4. 执行流程（两段式，减少打断）

### 阶段 1 · 自动段（尽量无人值守）
按 plan 任务卡顺序执行所有 A 类：
  W-1 后台失败任务对账（npm run task:status，确认已解决过程产物后登记清账）
  W-2 状态与 canonical 复核（state / docs:check / AUDIT-LOG 现读，核对 charter §4 工作面索引）
  W-3 只读探针与材料核实（如 GLB extras schema 探针——仅输出报告，不装依赖；若必须装包才能探针，则该子项改列 B 类，不擅自装）
  W-4 把执行中遇到的 B 类事项边跑边收集到「裁决批次清单」，但不立即打断
每完成一项：红绿→实现/核实→门禁→证据落 acceptance/→canonical 回写→（如适用）commit。

### 阶段 2 · 集中裁决与裁决后推进
触发时机（满足任一即提交批次，不再零散打断）：
  - 所有 A 类任务收口且有当前证据；或
  - 继续推进必须等待裁决（A 类已全部做完，无其它可自动项）。
提交动作：按第 5 节格式输出一份「裁决批次单」，一次性列出全部 B 类，然后停止等待用户批复。
用户批复后：按裁决结果推进工程包（③ W11 → ④ 3D），仍守单包串行；观感项保持 in_progress 不代签，不阻塞其它已裁决项。

## 5. 集中裁决提交格式（裁决批次单）
输出一份结构化清单，每项一行/一段，字段固定：
  [B-n] 事项：<一句话>
        分类依据：<命中哪条 B 类标准>
        现状：<canonical 出处 + 当前状态>
        候选：<用 | 分隔的选项>
        推荐：<Agent 建议 + 一句话理由（advice，不代替用户裁决）>
        影响：<裁决后触发什么 / 不裁会阻塞什么>
        需你：<批复选项 + 日期>
末尾给"一次性批复模板"：用户可写「B1=A, B2=维持, B3=暂缓, B4=你定」等，Agent 按批复逐项回写。
观感项（UI-706/707）在批次单中标注「签字槽，Agent 不代签，需你实机过目」，不提供"代签"选项。

## 6. 越权风险防范（红线）
- B 类未得用户批复前：不安装依赖、不引包、不改 manifest、不改产品默认语义、不开工程包。
- 观感项一律 pending_human_eye；**任何情况下不代签、不把主观验收写成 verified**。
- 不用 Jev/模型建议替代用户裁决——推荐只是 advice。
- C 类立即停，不为了"批量"而把保护性停止塞进批次跳过。
- 不把 external-blocked / 未跑的门冒充通过；不删改用户 untracked 资产。
- 不越 charter §2.2 范围外（G1+ / 自研引擎 / 打包分发 / Result Studio 资格线）。

## 7. 最终交付物结构与验收
交付物：
  1) 自动段成果清单：每项 A 类的结果 + 证据路径（acceptance/）+ 门禁读数；
  2) 裁决批次单：全部 B 类，按第 5 节格式，含一次性批复模板；
  3) 未执行项清单 + 原因（C 类停止项、暂缓项）；
  4) external-blocked / 既有红清单（如实标注，不冒通过）；
  5) canonical 回写记录：六件套逐项状态；
  6) 下一步提示（Jev 单一建议 + 母纲波次 + 全局 charter 进展）。
验收标准：
  - A 类：任务卡步骤全执行或有明确 external-blocked；门禁绿；证据在册；回写完成；
  - B 类：全部进批次单、零代答；观感项零代签；
  - 整体：npm run state 工作区可恢复、无未决 WIP 混淆；docs:check 仅剩既有已知红；
  - 不提前宣布完成：批次单未被批复前，整体任务状态=「自动段完成 + 待用户裁决」，不是"全部完成"。

## 8. 结束条件
自动段：A 类全收口 + 裁决批次单输出 + 回写完成 → 阶段 1 结束（停，等批复）。
整体：B 类经用户批复、裁决后工程包按批复收口、观感项如实保留签字槽、最终报告输出 → 全部完成。
```

## 设计说明（给人看，不属于提示词本体）

- **两阶段而非全预置**：旧版假设所有裁决都能预置默认值；本版承认 U-3D-D1~D5、观感签字等**不可预置**，改为"自动段先榨干、裁决攒一批"——这是减少打断的关键。
- **三分类判定前置**：每步先判 A/B/C，避免"边做边发现要问用户"的反复。
- **观感红线硬编码**：B 类判定第 1 条 + 越权第 2 条 + 交付验收，三处共同保证 `pending_human_eye` 不被代签。
- **保护性停止优先于批量**：C 类不被"减少打断"吞掉——安全/破坏性/用户资产永远立即停。
- **可验证**：每类事项有判定标准、每个阶段有结束条件、交付物有结构、验收有清单。
