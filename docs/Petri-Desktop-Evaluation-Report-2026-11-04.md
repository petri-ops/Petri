## §0 一句话总判

**工程成熟度 A-（≈4.2/5），产品兑现度 C+（≈2.6/5）。**

项目已经充分证明「**我们实现了很多**」，仍未证明「**这些实现用户够得着、任务跑得完**」。
距上轮评估一个月，最大的变化是：**集成债被机械化清扫干净了，但"能力可用性"的验证层级没有随之升级**。

## §3 七维度：需要完善的内容与优化方向

### 3.1 功能完整性 —— **4/5**

**已具备**：115 工具全链路（定义→契约→handler→元数据→三档可达），285 路由全挂载，168 IPC 无死通道，设置面板五段新接（白名单/原因码/环境包/Agent 审计撤销/记忆策略），联邦作业、钉住多格式预览。

**缺口**：
- **任务级闭环未验证**：工具都通，但"用户给一个目标 → agent 自主跑完"没有验收面。
- **13 条 UI 仅缺实机证据**（UI-382~390 条件腿、458/459/471/526/532/535/389）：代码完成但未实机，台账长期挂起。
- **扩展生态可用性未核**：插件/技能/MCP 货架「可见不可用」（上轮判词，本月未动）。

**优化方向**：从「功能面清扫」切换到「任务面验收」；把"缺实机证据"从永久挂起改为集中清偿。

### 3.2 代码质量 —— **4/5**

**已具备**：`lint` 0 error（2265 warnings 在基线内）、`types` 0、arch-cycles / css-modules / secret 全绿、knip 327 键冻结无新增、code-size 棘轮（24 文件 23,416 行）。

**缺口**：
- **热点文件偏大**：`SimpleChat.tsx` 2051 行（贴基线）、`conversationRunStore.ts` 817 行、`Federation.tsx` 600+。每次功能接入都在给这些文件"续命"。
- **两种参数来源并存**（`args.X` 与 `ctx` 注入 / 整体透传），静态规则无法区分，曾导致一次检测误判（已否决并留注释）。
- **EHD ≈1.0**（债新增/清偿比）：靠棘轮硬撑，新增速度与清偿速度持平，没有净下降。

**优化方向**：热点文件拆分预算（>800 行需立项说明）；给"参数来源"建统一约定；把"净减债"纳入包验收（不只是"不新增"）。

### 3.3 性能 —— **2.5/5（最弱维度）**

**缺口**：
- **几乎没有性能基线**：启动耗时、长会话 DOM 成本（UI-656 挂起）、大文件/大数据集（UI-389 需 500+ 文件夹具）、打包态性能，**均无度量**。
- 现有门禁全是"正确性"门，**没有"性能退化"门**。

**优化方向**：建四条性能基线（冷启动 / 长会话 1000+ 消息 / 500+ 文件项目 / packaged 启动），并入 closeout 作棘轮；先测量再优化，不预设问题。

### 3.4 可维护性 —— **4/5**

**已具备**：460 登记文档、canonical 单一源、`docs:check` + `reconcile` 双门、impact-map、汇编契约、AUDIT-LOG 决策留痕。

**缺口**：
- **高 churn**：958 提交/月、代码 31 万行且仍涨。维护成本在累积，但"是否该继续加"没有判据。
- **文档与实现偶发不同步**：344/345 的队列状态滞后，本月手工修过两次（说明自动对账不足）。
- **AUDIT-LOG 122KB 贴近单读上限**，频繁触发 compact 自稳。

**优化方向**：设"功能冻结窗口"（任务面未验证前不开新域）；队列状态改由 registry 单向生成（消手工同步）；AUDIT-LOG 改"摘要 + 指针"强制形态。

### 3.5 安全性 —— **4/5**

**已具备**：审批链工具无关（T1）、`external-request` 归类纠正（远程执行/写库不再逃逸）、IDE MCP 契约单源 + confirm 闸、secret 扫描、Keychain/0600、截图落盘白名单。

**缺口**：
- **MCP 通道无会话档位**：外部 IDE 调用 `ide_*` 写工具只有 `confirm` 布尔，无 `accessMode` 概念（本轮尝试进程档位，用户裁决取消）。
- **只读档的外部请求面**需要显式审计（`browser_act` 读动作放行合理，但要有记录）。
- **权限档与工具的映射**仍靠契约表人工维护，缺"新工具忘登记即红"的全链门（已有 assembly，但契约/元数据靠人补）。

**优化方向**：MCP 握手期协商档位（协议层）；外部请求审计面；契约/元数据缺省即 fail-closed。

### 3.6 文档 —— **4/5**

**已具备**：460 登记文档、规划/收口/审计三态、决策原话留痕、矩阵与报告落盘。

**缺口**：
- **全是工程向文档，没有"当前能做什么"的用户向能力地图**（新用户/新会话无法快速判断能力边界）。
- 历史文档 432 份 .md，检索与去重成本高。

**优化方向**：产出一份**面向使用者的能力地图**（按任务组织，不按工具组织），由矩阵自动生成；工程文档继续 canonical。

### 3.7 测试覆盖 —— **3.5/5**

**已具备**：976 测试文件、汇编契约、负测（红绿双样本）、矩阵棘轮、UI 台账 624 个带证据编号。

**缺口**：
- **测试集中在工具级/契约级，缺任务级与 E2E**：没有"用户目标 → 完成"的自动化验收。
- **证据资产化率低（EAR≈10%）**：acceptance 1919 文件里，进 closeout / 可复跑探针的比例低，大量证据是"一次性笔录"。
- **13 条 UI 仅缺实机证据** = 测试面断层的最直观表现。

**优化方向**：建**通用任务基准集**（跨域，非生信），度量自主完成率与干预次数；把验收证据从"笔录"升级为"可复跑探针"，EAR 目标 10% → 40%。
