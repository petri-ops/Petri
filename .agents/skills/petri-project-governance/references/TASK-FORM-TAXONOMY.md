# Task Form Taxonomy — 任务形态谱系与路由

> 目的：让任何一项工作在**登记之前**先回答「它算什么形态」，使流程重量与范围匹配——
> 既不让小改动背负立项仪式，也不让大面溜进无治理的快车道。
> 本文件是方法层（host-agnostic）：不变量、路由问题、分轨判据、迁移规则可移植到任何仓；
> 各台账与先例锚点是宿主仓的**运行数据**（本仓：AUDIT-LOG / ui-productization-audit /
> DOC-REGISTRY / roadmap）。移植到其它仓时先过 **§6 移植清单**。

**目录**：§0 不变量 · §1 主轴三问 · §2 主轨两分（BLOCK vs UI） · §3 辅助形态模式库 · §4 形态迁移 · §5 登记自检 · §6 移植清单（PORTING）

## 0. 不变量（先于一切形态，任何形态不得豁免）

1. **流程重量 ∝ 范围 × 周期 × 证据形态**：形态选择的第一原则是匹配，不是偏好。
2. **每种形态必须有唯一账本锚点**：工作留痕可恢复、可对账；「轻量」简化的是文档形态，
   不是验收义务。
3. **形态迁移必须留痕**：升级/降级在原条目写明去向与理由；禁止换形态洗掉验收义务，
   禁止同范围两本账。

## 1. 主轴三问（任何工作先过这三问）

- **Q1 产出是什么？**
  - 功能 / 修复 → 继续 Q2；
  - 结论 / 真相（调查、归因、对照实验）→ **专项**；
  - 能力沉淀（把反复出现的方法固化为 skill / 门禁）→ **制度化**；
  - 暂不做但值得记住 → **候选池**。
- **Q2 一次会话能收口吗？有单一验收边界吗？**
  - 是 → 主轨道（Q2a：界面体验面走 **UI 轨**；其余——测试债、安全加固、文档工程等——走**轻量包**）；
  - 否（多工作面 / 跨会话 / 有架构或数据模型裁决）→ **BLOCK**。
- **Q3 是新问题还是重演？**
  - 新问题 → 按 Q1/Q2 正常路由；
  - 同类第二次出现 → 先修，随后按「Convert recurring defects into gates」评估制度化升格。

## 2. 主轨两分（BLOCK vs UI）

| | BLOCK 完整工作包 | UI 增量 |
| --- | --- | --- |
| 范围 | 多工作面，P0-Pn 分阶段跨会话 | 单一体验面，单会话闭环 |
| 边界 | 新能力面 / 数据模型 / 架构调整 | 现有能力的**呈现重组**，通道与数据已存在 |
| 登记 | 独立 plan 文档 + 注册表 + roadmap + 审计台账立项行 | UI 台账一行，与实现同提交 |
| 启动 | planned 排队 + 用户显式裁决 + P0 评审 | 用户反馈即裁决，直接开工 |
| 验收 | 阶段门禁 + closeout 聚合 + acceptance 证据目录 | 定向/组件测试 + 实机 + 台账翻 verified |

**分轨判据（正面回答「这活为什么是 UI 不是 BLOCK」）：**

1. 文件面是否收敛在单一模块区？呈现是否只重组既有通道与数据、不新增管道？→ 是则 UI 轨合身。
2. 是否需要多裁决项的 P0 评审？是否需要跨会话串行分阶段？→ 是则 BLOCK。
3. **分轨线不在前后端**：动了服务端但边界单一、单会话可收口的，仍是合法 UI 增量
   （先例：UI-384 工具输出服务端格式化镜像 + 落库，仍走 UI 轨当日闭环）。

## 3. 辅助形态（开放模式库）

每种形态 = 用途 + 进入判据 + 账本锚点 + 先例锚点。新形态按同一模式登记后入册，
本表不是封闭清单——没有先例的新形态，按最近似形态登记并在条目内声明差异。

| 形态 | 用途 | 进入判据 | 账本锚点 | 本仓先例 |
| --- | --- | --- | --- | --- |
| 轻量包 | 有独立边界但撑不起多阶段 plan | 一条台账条目即可承载全范围+验收 | AUDIT-LOG 条目即 plan | TEST-INFRA-DEBT、BLOCK-85 |
| 专项 / 归因 | 调查、归因、对照实验；产出是结论不是功能 | Q1 = 结论 | AUDIT-LOG 条目（可附归因/评审文档） | UI341-A7-ATTRIBUTION |
| 立项评审稿 | planned 前置：先出评审文档列 D1-Dn 待裁决 | 大面需逐项裁决、但未到启动 | 独立评审文档 + 注册表 | BLOCK-85/88 P0 评审稿 |
| 修复批 | 用户多条反馈打包一次闭环 | 单会话可全收口的多点小修 | UI 台账单条批注 N 项 | UI-400 六项批次 |
| 加映 N | 同包收口后的后续增量，不另立条目 | 仍在原 ID 范围内 | 原条目「加映 N」标题 | UI-304 加映三 |
| 对账收口 / superseded | 零新实现的账实对账；撞号并入他包 | 无产品代码改动，只动账 | 审计台账 + 注册表状态 | AGENT-WORKBENCH；BLOCK-99 撞车对账（9d47c922） |
| 制度化沉淀 | 同类教训第二次 → skill + 机械化门禁 | 触发 governance「Convert recurring defects into gates」 | skill 文件 + 门禁脚本 | CSS-THEME-SKILL |
| 候选池 | 想法登记、不开工 | 仅记录，启动需显式裁决 | roadmap/plan 登记行 | openclaw 对标候选池 |
| Goal 线 | Goal 级长线，下辖多包/多阶段 | 里程碑/资格型、跨数周 | 独立 Goal plan + 阶段台账 | G0-RS（P0-P7） |

## 4. 形态迁移（升级 / 降级规则）

- **UI → BLOCK**：实现中发现跨模块 / 数据模型变更 / 新增多裁决项 → **停手上报**，转立
  BLOCK（planned）排队；UI 条目留转出说明。禁把大面拆散硬塞 UI 轨。
- **BLOCK → 轻量包**：P0 评审后实际范围缩水 → plan 退化为条目并登记说明，不废编号。
- **BLOCK 内 deferred**：未启动工作面必须用户显式裁决 `deferred` 并回写 plan 状态头，
  禁「半拆无主」状态跨包存续。
- **反模式**：借「加映」无限扩范围（加映是同 ID 增量，不是新范围的免检通道）；
  借「修复批」夹带架构变更；借「专项」绕过功能验收直接改产品代码。

## 5. 登记自检（每次定形态后、收口前各过一遍）

- [ ] 账本锚点存在，且与实现**同提交**登记；
- [ ] 验收证据形态与该形态匹配：UI=实机+台账 verified；BLOCK=阶段门禁+acceptance 目录；
      轻量包=条目内声明的验收逐项对账；专项=结论被 canonical 文档引用；对账=账实一致；
- [ ] 如有形态迁移，原条目已写明去向与理由；
- [ ] 该形态的既定门禁（如 docs:check / ui:audit:check / closeout）按其规则执行完毕。

## 6. 移植清单（PORTING）

> 把本谱系移植到另一个仓时，**按序过完本清单再启用**。移植成本目标：半小时内。
> 先例：`petri-dev-infra/PORTING.md`（跨仓复用的同款思路）。

- [ ] **账本引导先行（最关键）**：确认宿主仓已有两本账的等价物——「审计台账」（本仓=
      `AUDIT-LOG.md`）与「增量台账」（本仓=UI 台账）。没有先建账再移植：
      **无账本的分类产生治理幻觉**（有分类、无留痕），比不分类更糟。
- [ ] **快轨道改名**：按宿主产品形态重命名「UI 轨」（如 CLI/纯后端仓 → patch 轨 / docs 轨），
      §1 Q2a 与 §2 表头同步改写。
- [ ] **先例列重积**：清空 §3「本仓先例」列，或换成本仓第一批真实先例。先例是例证不是规范，
      格物的历史对其它仓只是噪声。
- [ ] **裁决指涉改写**：无人值守 / 无用户在环的仓，把全文「用户显式裁决」改写为
      「守门人角色裁决」，并在宿主治理文档写明守门人是谁、超时默认行为是什么。
- [ ] **门禁接线**：把 §5 自检引用的门禁命令（本仓=docs:check / ui:audit:check / closeout）
      映射到宿主仓的真实命令；宿主没有的门禁如实删除对应自检项，不虚设。
- [ ] **命名与编号对齐**：「BLOCK-###」编号约定、台账条目格式按宿主习惯替换；
      §0–§2、§4 的方法层内容不改。

**移植完成判据**：按 skill-creator Step 6 做一次 forward-test——派无上下文泄漏的子代理，
只给本文件 + 三个宿主真实工作请求，路由正确（形态+账本锚点+迁移规则）即移植完成；
路由含糊处优先修本文件的判据措辞，而不是事后口头补充。
