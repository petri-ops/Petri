# 事故复盘模板（Postmortem）

> 适用：实机验收抓真、生产路径回归、环境事故、误操作波及用户数据等任何"结果与预期不符且已登记"的事件。
> 闭环目标：每份复盘必须回答"教训去了哪"——进环境纪律 / 进检查单 / 转化为门禁，三选一，不允许"仅记录"。
> canonical 依据：`$petri-project-governance` SKILL.md §"Convert recurring defects into gates"。

## 复盘骨架

```markdown
## 事故：<一句话事实标题>（YYYY-MM-DD）

**现象**：观察到什么（可复现步骤 / 证据文件:行 / 断言输出）
**影响面**：波及了什么（用户数据 / 在制工作 / 交付物可信度），已如何止损
**根因**：为什么会发生（技术根因，非"注意力不够"）；为何既有门禁没拦住
**教训去向**（三选一，可多选）：
- [ ] 环境纪律：写进 AGENTS.md / 启动检查单环境段（如"后端变更后必须重启 dev Electron"）
- [ ] 检查单：写进 LAUNCH / CLOSEOUT / 评审检查单具体条目
- [ ] 转化为门禁：定向测试 / harness 检查 / dev-verify flow（按回归→门禁规则执行，并在门禁内写明映射）
**登记**：AUDIT-LOG 条目链接 / 提交哈希
```

## 填写纪律

- 根因追问到可操作的层：拦不住它的门禁缺了什么，而不是"下次小心"
- 同类事故第二次出现 = 前一次的"教训去向"没落地——先补落地，再写新复盘
- 涉及用户数据的（先例：BLOCK-UI-LEDGER 误删 dev 会话），止损动作与恢复证据必须留痕
- 复盘不是追责：写事实与机制缺口，不写"谁的锅"
